# FRIDAY — план реалізації голосового асистента (Windows)

> Цей файл — технічне завдання для AI-агента (Antigravity). Працюй **поетапно**: після кожного етапу зупиняйся, запускай тести, показуй результат і чекай підтвердження переходу до наступного. Нічого не встановлюй глобально і не змінюй файли поза папкою проєкту без запиту.

---

## 1. Мета

Локальний фоновий голосовий асистент для Windows, який:

1. прокидається **лише за гарячою клавішею** (hold-to-talk), у спокої майже не використовує CPU/RAM;
2. керує вікнами й моніторами: переміщення, збільшення/зменшення, напівекран, фокус, запуск програм;
3. вводить текст там, де вказано (поле в активному вікні, Telegram-повідомлення);
4. шукає в Google й на конкретних сайтах;
5. **«Помилка → документація»**: користувач копіює помилку з коду, асистент відкриває відповідну сторінку документації на іншому моніторі;
6. складні/кодерські задачі передає в Antigravity CLI.

Мова користувача: **українська** (із вкрапленнями англійських технічних термінів: `FastAPI`, `traceback`, `git`).

## 2. Принципи (пріоритети від вищого до нижчого)

1. **Швидкість**: детермінована дія має виконуватись за < 150 мс після завершення розпізнавання.
2. **Мінімальне навантаження**: один процес, жодних постійних важких моделей у пам'яті без потреби, жодного polling у циклі.
3. **Безпека**: незворотні дії — тільки з підтвердженням (див. розділ 9).
4. **Простота й розширюваність**: кожна можливість — окремий «навичок» (skill) за єдиним інтерфейсом.
5. **Спостережність**: кожен крок логується з таймінгами, щоб легко знаходити лаги.

## 3. Архітектура

### 3.1 Два контури

- **Fast path (детермінований)** — правила/регулярки → пряма дія через Win32 API. ШІ не викликається.
- **Smart path (LLM-парсер)** — якщо правило не спрацювало, швидка модель (Gemini Flash) перетворює текст на **структурований JSON-виклик навички**. Модель *не* пише довгих відповідей, лише JSON.
- **Agent path (важкий)** — запити типу «напиши скрипт», «відрефактори файл», «поясни помилку» передаються в Antigravity CLI.

### 3.2 Потік даних

```
[Hold hotkey] → [Audio capture] → [STT] → [Router]
                                              │
        ┌─────────────────────────────────────┼───────────────────────────┐
        ▼                                     ▼                           ▼
  Fast rules (regex)                  LLM → JSON command           Agent (Antigravity CLI)
        │                                     │                           │
        └──────────────► [Skill registry / Executor] ◄────────────────────┘
                                      │
                         [Confirm gate] (для ризикових дій)
                                      │
                         [Feedback: toast / короткий звук]
```

### 3.3 Автомат станів

`IDLE → LISTENING → TRANSCRIBING → ROUTING → (CONFIRMING) → EXECUTING → IDLE`

- Нова гаряча клавіша під час `EXECUTING` не ігнорується мовчки: або скасовує поточну дію (для довгих), або ставиться в чергу.
- Будь-який збій повертає в `IDLE` і показує коротке сповіщення з причиною.

### 3.4 Потоки

- **Main thread:** asyncio event loop (роутер, виконавець, мережеві виклики).
- **Hotkey thread:** слухач клавіатури (`pynput`), кладе події в `asyncio.Queue` через `loop.call_soon_threadsafe`.
- **Audio callback thread:** `sounddevice.InputStream`, пише чанки в буфер.
- Жодних інших постійних потоків. Блокуючі виклики (Win32, subprocess) — через `asyncio.to_thread`.

## 4. Технологічний стек

| Задача | Бібліотека |
|---|---|
| Мова | Python 3.11+ |
| Гарячі клавіші | `pynput` (hold-to-talk потребує події press/release) |
| Запис звуку | `sounddevice` + `numpy` (16 кГц, mono, int16) |
| STT (за замовчуванням) | Gemini (аудіо через API), інтерфейс-обгортка |

| LLM-парсер | `google-genai`, швидка Flash-модель, вивід лише JSON |
| Вікна/монітори | `pywin32` (`win32gui`, `win32con`, `win32api`, `win32process`) |
| Буфер обміну | `pyperclip` або `win32clipboard` |
| Сповіщення | `winotify` (toast) |
| Telegram | `telethon` (через API, не через емуляцію кліків) |
| Конфіг | `tomllib` (`config.toml`) + `.env` для ключів |
| Валідація | `pydantic` v2 |
| Логи | стандартний `logging`, ротація файлів |
| Тести | `pytest` |

> Перед використанням перевір актуальні назви моделей і API у документації постачальника — не покладайся на пам'ять.

## 7. Схема команд (контракт між роутером і навичками)

LLM-парсер і fast-rules повертають один і той самий об'єкт:

```json
{
  "skill": "window.move",
  "args": { "target": "browser", "monitor": 2, "mode": "maximize" },
  "confidence": 0.93,
  "needs_confirm": false
}
```

Допустимі `skill` (початковий набір):

| skill | args | Приклад фрази |
|---|---|---|
| `window.move` | target, monitor, mode (`maximize`/`left`/`right`/`center`) | «перенеси браузер на другий монітор» |
| `window.resize` | target, mode (`bigger`/`smaller`/`maximize`/`restore`) | «збільш це вікно» |
| `window.focus` | target | «перейди в термінал» |
| `app.launch` | name | «відкрий телеграм» |
| `web.search` | query, site? | «знайди в гуглі як зробити X» |
| `docs.lookup` | source (`clipboard`/`query`) | «покажи документацію по цій помилці» |
| `text.type` | text | «напиши: привіт, зустрінемось о шостій» |
| `telegram.send` | contact, text | «напиши Олегу в телеграм, що я запізнюсь» |
| `agent.run` | prompt | «відрефактори цей файл» |
| `clarify` | question | якщо команда неоднозначна |

Правила парсера:

- Вивід **тільки валідний JSON** за pydantic-схемою; при невалідному — один ретрай, потім `clarify`.
- Якщо `confidence < 0.7` → `clarify`, а не вгадування.
- Невідомі навички відкидаються.

## 8. Етапи розробки

Кожен етап має **критерії готовності (DoD)**. Не переходь далі, поки вони не виконані.

### Етап 0 — Каркас
- Створити структуру з розділу 5, `pyproject.toml`, віртуальне середовище, `config.py`, логування.
- `timing.py`: контекстний менеджер для вимірювання тривалості кроків.
- **DoD:** `python -m friday` запускається, читає конфіг, пише лог, коректно завершується по Ctrl+C.

### Етап 1 — Гаряча клавіша й запис
- `hotkeys.py`: hold-to-talk (`press` → старт запису, `release` + `tail_ms` → стоп).
- `audio.py`: запис 16 кГц mono, жорсткий ліміт `max_seconds`, відкидати запис коротший за ~300 мс.
- Звуковий/візуальний індикатор початку й кінця запису (`feedback.py`).
- **DoD:** утримання клавіші в будь-якій програмі (включно зі згорнутим терміналом) записує аудіо; CPU у спокої ≈ 0%; запис зберігається у `temp/` для перевірки.

### Етап 2 — STT
- Інтерфейс `Transcriber.transcribe(audio) -> str`.
- Реалізація `gemini.py` (повторно використовувати HTTP-клієнт, не створювати новий на кожен запит) і `whisper_local.py` (модель завантажувати **лише** якщо обрано цей бекенд; прогрів при старті).
- Промпт/підказка для STT: транскрибувати дослівно українською, англійські технічні терміни залишати латиницею.
- **DoD:** 10 тестових фраз розпізнаються; затримка від відпускання клавіші до тексту виміряна й записана в лог.

### Етап 3 — Менеджер вікон (fast path, без ШІ)
- `util/monitors.py`: `EnumDisplayMonitors`, `GetMonitorInfo` (**work area**, а не повний розмір), увімкнути DPI awareness на старті (`SetProcessDpiAwareness`).
- `skills/windows.py`:
  - `find_window(target)`: за назвою процесу/заголовком; кеш HWND з перевіркою `IsWindow`.
  - `move_to_monitor(hwnd, idx, mode)`: спочатку `ShowWindow(SW_RESTORE)`, потім `SetWindowPos`; для `maximize` — `SW_MAXIMIZE` після переміщення.
  - `snap(hwnd, left|right|center)`, `resize(hwnd, bigger|smaller)` (крок 10–15% від work area).
  - Врахувати невидимі рамки вікон Windows 10/11 (`DwmGetWindowAttribute` + `DWMWA_EXTENDED_FRAME_BOUNDS`).
  - `focus(hwnd)`: надійний `SetForegroundWindow` (обхід обмеження через `AttachThreadInput` або короткий Alt-трюк).
- `skills/apps.py`: запуск **лише** з білого списку `config.toml`.
- **DoD:** ручний CLI-тест `python -m friday.dev window move browser 2 maximize` працює на двох моніторах; виконання < 100 мс.

### Етап 4 — Роутер
- `rules.py`: словник синонімів + регулярки для україномовних команд («перенеси/перекинь/відправ», «на другий/інший/лівий монітор», «збільш/зменш/розгорни», «відкрий/запусти»). Нормалізація тексту: нижній регістр, прибрати пунктуацію, прості закінчення.
- `llm_parser.py`: системний промпт (див. розділ 10), схема JSON, `temperature=0`, короткий `max_output_tokens`, таймаут 5 с.
- Логіка: `rules` → якщо `None` → `llm_parser` → якщо `skill == agent.run` → `agent_cli`.
- **DoD:** набір із 30+ тестових фраз у `tests/test_router.py`; ≥ 80% обробляється fast path; всі дії проходять валідацію схеми.

### Етап 5 — Введення тексту й вебпошук
- `typing_text.py`: вставка через **буфер обміну + Ctrl+V** (швидше й надійніше для кирилиці, ніж емуляція натискань); зберегти попередній вміст буфера й відновити після вставки.
- `web.py`: `web.search` будує URL пошуку (з `site:` за потреби) і відкриває в браузері за замовчуванням; `web.open` для відомих сайтів із конфігу.
- **DoD:** «напиши: …» вставляє текст у активне поле (Notepad, VS Code, Telegram); «знайди в гуглі …» відкриває пошук.

### Етап 6 — Помилка → документація
- Хоткей `explain_clipboard`: прочитати буфер обміну → обрізати до розумної довжини (останні ~40 рядків traceback + перший рядок помилки).
- Спершу **евристика без ШІ**: розпізнати тип помилки (`ModuleNotFoundError`, `TypeError`, `KeyError`, помилки FastAPI/pydantic тощо) і бібліотеку з рядків traceback.
- Якщо евристики недостатньо — один виклик LLM: повернути JSON `{ "library": ..., "error": ..., "query": ... }`.
- Побудувати запит: `<error text> site:<docs домен з конфігу>`; відкрити **нове вікно браузера**, дочекатися його появи (порівняти набір HWND до/після) і перемістити на монітор `docs`.
- Не крадіжка фокусу: після переміщення повернути фокус у попереднє вікно (редактор).
- **DoD:** скопіювати типовий traceback → за ≲ 2 с відкривається релевантна сторінка на другому моніторі, фокус лишається в редакторі.

### Етап 7 — Telegram
- `telethon`: одноразова авторизація, сесія зберігається локально (файл сесії не комітити).
- Розв'язання контакту: нечіткий пошук за ім'ям серед діалогів (кешувати список діалогів).
- **Обов'язковий confirm gate:** показати toast «Олегу: "…" — відправити? (Enter / Esc)» і слати лише після підтвердження.
- **DoD:** повідомлення надходить правильному контакту; без підтвердження нічого не надсилається.

### Етап 8 — Інтеграція Antigravity CLI
- `agent_cli.py` — **адаптер** з конфігованою командою; перед реалізацією виконати `antigravity --help` і зафіксувати реальні прапорці (не вгадувати).
- Передавати промпт аргументом/через stdin, у робочій директорії активного проєкту (визначити за заголовком вікна редактора або з конфігу).
- Вивід показувати користувачеві; будь-які зміни файлової системи — лише після ручного підтвердження. **Режими auto-approve/--yes не використовувати.**
- **DoD:** голосова команда «відрефактори файл X» відкриває сесію CLI з правильним промптом і чекає на підтвердження.

### Етап 9 — Безпека, надійність, оптимізація
- `safety.py` (див. розділ 9), перевірка списку заборонених патернів у всьому, що йде в shell/CLI.
- Профілювання: таблиця затримок по етапах (запис → STT → роутер → дія), пошук вузьких місць.
- Автозапуск (Task Scheduler / ярлик у Startup) у режимі без консолі (`pythonw`), іконка в треї (необов'язково).
- Обробка винятків: жодна помилка навички не валить основний цикл.
- **DoD:** 1 година роботи у фоні без витоку пам'яті; CPU у спокої < 1%; усі тести зелені.

## 9. Безпека

1. **Білий список програм** — жодного `subprocess.Popen(f"start {user_text}")`. Тільки ключі з `config.toml`.
2. **Confirm gate** обов'язковий для: надсилання повідомлень, будь-яких змін файлів через CLI, видалення, git-операцій, що переписують історію.
3. **Заборонені/підтверджувані патерни:** `rmdir /s`, `del *`, `format`, `reg add/delete`, `git reset --hard`, `git push --force`, `rm -rf`. Блокувати автоматично, дозволяти лише ручним підтвердженням.
4. **Помилки розпізнавання:** якщо транскрипт короткий, схожий на шум або `confidence` низький — перепитати, а не виконувати.
5. **Ліміт запису 15 с** — захист від залипання клавіші.
6. **Права:** запускати від звичайного користувача. Якщо цільове вікно працює з правами адміністратора, керувати ним без прав адміна неможливо (UIPI) — повідомити про це, а не падати.
7. **Секрети** — лише в `.env`, у `.gitignore`; не логувати ключі й вміст буфера обміну повністю.
8. **Приватність:** аудіо та транскрипти не зберігати довше, ніж потрібно; тимчасові файли видаляти.

## 10. Системний промпт LLM-парсера (чернетка)

```
Ти — парсер голосових команд для асистента на Windows. Користувач говорить українською.
Перетвори команду на ОДИН JSON-об'єкт за схемою { skill, args, confidence, needs_confirm }.
Відповідай ТІЛЬКИ JSON, без пояснень і без markdown.
Допустимі skill: window.move, window.resize, window.focus, app.launch, web.search,
docs.lookup, text.type, telegram.send, agent.run, clarify.
Якщо команда неоднозначна — skill = "clarify" з полем args.question.
Дії, що надсилають повідомлення або змінюють файли, мають needs_confirm = true.
```

## 11. Бюджет затримок (цільові значення)

| Етап | Ціль |
|---|---|

## 12. Правила для агента, що пише код

- Типізація (`typing`), pydantic для всіх схем, короткі функції, докстрінги українською.
- Кожна навичка має юніт-тест; Win32-частину ізолювати за тонким шаром, щоб логіку можна було тестувати без вікон.
- Усі таймаути мережевих викликів задавати явно.
- Не додавати залежності без потреби; перед додаванням нової — коротко обґрунтувати.
- Після кожного етапу: оновити `CHANGELOG.md`, запустити `pytest`, показати таблицю виміряних затримок, а після успішного проходження тестів зробити `git commit` і `git push` нових файлів та змін у репозиторій `https://github.com/vavun/Friday.git`.
- Якщо щось у цьому плані суперечить реальній поведінці бібліотеки/CLI — зупинитись і запитати, а не вигадувати обхід.

## 13. Подальші ідеї (після базової версії)

- Контекст «що в фокусі» (назва активного вікна/проєкту) для точнішого роутингу.

- Профілі розкладки моніторів («режим кодингу»: редактор ліворуч, документація праворуч).
- Історія команд і «повтори останню дію».
- Нові навички через реєстр без змін ядра.
